1. 全局读取优先级和页面文档打架 ⚠️ 最该修

SKILL.md 说“优先 bsk extract table，读不干净再用 read-table.js”。SKILL.md:45

但竞品分析和选产品页明确写了：extract table 对 div 表格读不出行，必须用 read-table.js。references/pages/competitor-lookup.md

新 agent 先读 SKILL.md，很可能先在竞品页白试一次 extract table。

改法：在 SKILL.md 的读取步骤加一句“以页面文档指定的读取方式为准；页面文档没写时，才按下面的默认顺序”。最好再给一张“页面 → 读取方式”的小表。

2. --until-visible 可能被上一次结果误触发 ⚠️ 隐蔽但危险

workflow.md 的示例用了 .el-table__body-wrapper tbody tr 作为等待锚点。references/workflow.md

问题是：重新查询时，旧结果的行本来就是可见的，bsk step 会立刻返回，agent 接着读到上一轮的数据。文档虽然提醒“必须是动作后会变可见的锚点”，但示例本身在复查询场景下不成立。

改法：加一个“陈旧结果防护”：

查询前记录 total + 首行 ASIN/关键词作为签名；
动作后等 300–500ms，读一次；签名没变就再等一次，最多 3 次；
仍没变就判定“查询没生效”，去观察遮罩/提示，而不是直接报数。
这比单纯依赖 CSS 锚点可靠。

3. 额度护栏不够具体

红线只写了“批量/重复查询先问用户”。SKILL.md:15 建议加硬阈值：单轮 ≤ 10 次查询、翻页 ≤ 3 页、导出必须单独确认；出现额度提示立即停。成本是需要考虑的因素，这条能防止 agent “为了凑数反复翻页”。

4. observe 截断的处理没写进主流程

验证记录里已经发现 observe 对查询栏的自定义组件语义暴露不完整，需要 --cursor 或提高 --max-tokens。docs/verification/bsk-preflight.md

但 SKILL.md 只写了 --max-tokens 4000，没写“截断了怎么办”。建议补一句：“输出末尾被截断或缺少目标控件时，用 --cursor 继续或提高到 8000；不要因为没看到就认为控件不存在。”

5. description 对 CA 的承诺略高于实际

description 写的是 “on Amazon US or CA”，但 CA 只有选产品跑过一次完整查询，其余 5 页只确认了站点控件存在。文档本身很诚实地标注了，但 description 是触发层，用户看不到这些限定。

改法：改成 “US（完整验证）/ CA（部分验证）”，或者在 SKILL.md 开头加一句“CA 仅选产品完成验证，其余页面按未验证对待”。
